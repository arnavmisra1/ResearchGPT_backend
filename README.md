# Chat with PDFs — Backend

FastAPI backend powering [Chat with PDFs](https://research-gpt-frontend.vercel.app), a RAG (Retrieval-Augmented Generation) application for having grounded, cited conversations with uploaded PDFs.

**🔗 Live API:** https://researchgpt-backend-1.onrender.com/docs
**🔗 Frontend repo:** [chat-with-pdfs-frontend](#)

> Hosted on Render's free tier — the service sleeps after periods of inactivity and takes ~30–60s to wake up on the next request.

---

## What it does

This service handles the full RAG pipeline and supporting features for the app:

1. **PDF ingestion** — extracts text, splits it into overlapping chunks, generates embeddings, and stores them in a vector database, scoped per document
2. **Retrieval-augmented chat** — embeds incoming questions, retrieves the most relevant chunks via semantic search, and streams a grounded LLM response with source page citations
3. **Conversation memory** — accepts and incorporates prior chat turns so follow-up questions work correctly
4. **Annotations** — stores highlight positions and notes per document, with precise coordinate data for accurate redraw
5. **Auto-summarization** — generates a short summary and topic tags for each document on upload, using structured LLM output
6. **PDF serving** — serves the raw uploaded PDF back to the frontend for in-browser rendering

## Tech Stack

- **FastAPI** — API framework, with Server-Sent Events for streaming responses
- **ChromaDB** — vector database for chunk storage and semantic retrieval
- **SQLite** — relational storage for annotations and document summaries
- **Groq** (Llama 3.1) — LLM inference for chat and summarization, via an OpenAI-compatible client
- **Hugging Face Inference API** — hosted text embeddings (`sentence-transformers/all-MiniLM-L6-v2`), used instead of running the model locally to keep the service lightweight on free-tier hosting
- **LangChain** — PDF loading (`PyPDFLoader`) and text chunking (`RecursiveCharacterTextSplitter`)

## API Endpoints

| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/upload` | Upload a PDF; extracts, chunks, embeds, stores, and generates a summary |
| `POST` | `/chat` | Ask a question about a document; streams a grounded, cited answer |
| `GET` | `/pdf/{filename}` | Serves the raw PDF file for in-browser rendering |
| `GET` | `/summary/{filename}` | Returns the auto-generated summary and topics for a document |
| `POST` | `/annotations` | Save a highlight/annotation with position data |
| `GET` | `/annotations/{filename}` | Retrieve all annotations for a document |
| `DELETE` | `/annotations/{annotation_id}` | Delete a single annotation |
| `DELETE` | `/document/{filename}` | Delete a document and all associated chunks/data |
| `GET` | `/health` | Health check |

Full interactive API documentation is available at `/docs` (Swagger UI, auto-generated by FastAPI).

## Running Locally

```bash
python -m venv venv
venv\Scripts\activate        # Windows
# source venv/bin/activate   # Mac/Linux

pip install -r requirements.txt
```

Create a `.env` file in the project root:
```
GROQ_API_KEY=your_groq_key
HF_API_TOKEN=your_huggingface_token
FRONTEND_URL=http://localhost:5173
```

```bash
uvicorn main:app --reload
```

The API will be available at `http://localhost:8000`, with interactive docs at `http://localhost:8000/docs`.

## Deployment

Deployed on [Render](https://render.com) as a Python web service.

- **Build command:** `pip install -r requirements.txt`
- **Start command:** `uvicorn main:app --host 0.0.0.0 --port $PORT`
- **Environment variables:** `GROQ_API_KEY`, `HF_API_TOKEN`, `FRONTEND_URL`, `PYTHONUNBUFFERED=1`

### Notable deployment considerations

- **Embeddings run via a hosted API, not locally.** An earlier version used `sentence-transformers` running in-process, which — combined with `torch` and ChromaDB's own default embedding model — exceeded the 512MB memory limit on Render's free tier. Switching to Hugging Face's hosted inference API removed these heavy dependencies entirely.
- **ChromaDB is configured with `embedding_function=None`**, since embeddings are always supplied externally; without this, ChromaDB silently loads its own default embedding model at startup, adding unnecessary memory overhead.
- **No persistent disk on the free tier** — uploaded files, the ChromaDB vector store, and the SQLite database do not survive a service restart. For production use, this would require a paid tier with persistent storage, or migrating to managed hosted equivalents (e.g., a hosted vector DB and Postgres).
